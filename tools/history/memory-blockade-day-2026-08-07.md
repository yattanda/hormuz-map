## 封鎖日数カウンター（blockadeDay）の起算日問題 — 調査結果と決定（2026-08-07）

> **【2026-10-02 追記】呼び名を「封鎖N日目」から「危機N日目」に改めた。**
> この節で決めたのは起算日（2/28）だけで、「何による封鎖を数えるのか」は決めていなかった。
> 調べ直すと、表記は「封鎖3日目」（4/16・米軍の封鎖起点）→「二重封鎖67日目」（5月・数字は 2/27 起点）→ 主語なしと変わっており、
> 2/28 から途切れずに続く単一の封鎖も記録上ない。数字の実体は開戦からの経過日数である。
> 起算日・計算式・「過去の速報本文は書き換えない」は変えていない。あわせて「封鎖」は必ず主語を付けて書くルールにした。
> 方針と直した場所：`tools/blockade-term-policy.md`／表記ルール：`.claude/skills/content-style-guide/SKILL.md`

### 結論

**`archive_timeline.json` は一切変更せず、`docs/archive/index.html` 側で日付から動的計算する方式を採用した。**
封鎖日数の起算日は **2026年2月28日を「1日目」** とする（2026-08-05 = 159日目）。

### 調査の経緯

2026-08-01時点のメモリーには「`archive_timeline.json` の既存エントリーが
4/13起算で計算されている可能性があり、後日まとめて全件を再計算する」と記録されていた。
2026-08-07に全142エントリーを実データ検証した結果、**この想定は誤りだった**ことが判明した。

### 実データ検証で判明した事実（全142エントリー）

| 起算日 | 該当範囲 | 件数 | 備考 |
|---|---|---|---|
| **4/13**（二重封鎖＝米港湾封鎖の開始日） | 4/16 のみ | **1件** | `blockadeDay: 3`。想定に反し1件のみだった |
| **2/27** | 4/30〜6/24 | 22件 | 現行基準比 +1 |
| **2/28**（現行の正） | 6/25以降 | 37件 | 正しい |
| （未設定 `null`） | 全期間に散在 | 82件 | スタンプが非表示になっていた |

- **6/24 と 6/25 がともに `118`** になっているのは、カウンタを1日据え置いて
  起算日を 2/27 → 2/28 に再同期した痕跡。**単純ミスではなく意図的な定義変更**である。
- **6/3 の `102`** のみ、旧基準（2/27起算なら97）でも説明できない単純入力ミス。
- JSONの `blockadeDay` と速報本文中の「封鎖◯日目」は **57/57件で完全一致**していた。

### 一括上書きを採用しなかった理由

1. **JSONと本文が100%一致しているため、JSONのみ修正すると
   「現時点で存在しない矛盾」を23件、新規に発生させる**ことになる。
2. 本文も含めて書き換えると、**過去に実際に公開した速報本文の改変**にあたる。
   起算日の変更は「当時の定義では正しかった数字」であり、誤記ではない。
3. 142件のフル上書きはデータ破損リスクが高い。

### 採用した解決策（2026-08-07 適用・push済み）

`docs/archive/index.html` に以下を追加し、`e.blockadeDay` への参照を全廃した。

```javascript
// 封鎖日数の起算日：2026年2月28日を「1日目」とする（月は0始まりのため 1 = 2月）
const BLOCKADE_BASE_UTC = Date.UTC(2026, 1, 28);
function calcBlockadeDay(iso){
  const [y, m, d] = iso.split('-').map(Number);
  return Math.round((Date.UTC(y, m - 1, d) - BLOCKADE_BASE_UTC) / 86400000) + 1;
}
```

**変更箇所（計4点）：**
- 関数定義の追加（`fmtJpDate()` の直後）
- `renderStats()` の統計欄：`entries.map(e => e.blockadeDay).filter(Boolean)` → `entries.map(e => calcBlockadeDay(e.date))`
- 各エントリーのスタンプ：条件分岐を撤去し `calcBlockadeDay(e.date)` を常時表示
- `renderRangeNotice()` に起算日の注記を追加

**効果：**
- 統計欄の異常表示 `3〜159日目` → `1〜159日目` に正常化
- スタンプ欠落82件が解消し、全142件に表示
- データ破損リスク・本文改変ともにゼロ
- 将来のエントリーで `blockadeDay` の記入精度を問う必要がなくなった

### 残存する既知の差異（許容）

23件のエントリーで「スタンプの数字」と「本文中の数字」が1日ずれる。
これは `renderRangeNotice()` に追加した以下の注記で読者に説明している。

> 封鎖日数は2026年2月28日を1日目として再計算した値を表示しています。
> 2026年6月24日以前の速報本文中の「封鎖◯日目」という表記は、
> 当時採用していた起算日（2月27日）に基づくため、
> スタンプの数字と1日ずれている場合があります。

### 運用上の教訓（重要）

**「〜の可能性がある」という推測をメモリーやドキュメントに残すと、
後日それが「確定した事実」として扱われ、誤った一括処理を招くリスクがある。**

2026-08-01に「4/13基準で汚染されている可能性」を実データ未検証のまま記録した結果、
本来不要かつ有害な一括修正が「予定タスク」として残り続けていた。

→ **対策：修正作業に着手する前に、必ず実データを検証してから方針を決定すること。
  推測を記録する場合は「未検証の仮説」であることを明示すること。**
