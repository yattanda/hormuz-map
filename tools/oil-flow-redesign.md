## 2. 問題点の整理

### 2-1. 最大の問題：算出方法が記録されていない

- `_comment` の一文（「tankers_week は週あたり寄港タンカー隻数推定」）以外、根拠が存在しない
- 元は Claude.ai へのプロンプトで生成した推定値。**プロンプトも出力も残っていない**ため、誰も再現も検証もできない
- 62 / 125 / 45 / 12 という数値が何から導かれたのか、現時点で説明する手段がない
- サイトは編集方針で算出根拠の公開を掲げており、この状態はその方針と整合しない

### 2-2. 4か月前の数値が公開され続けている影響

| 影響 | 深刻度 |
|---|---|
| ルートA が「稼働中62万BPD」と表示され、同じ行の本文と矛盾 | **高**（誤情報） |
| C_US「45万BPD」は5月の急増初期の値。7月のメキシコ産初便を織り込んでいない | 中（過小） |
| C_GL「12万BPD」は「本格化は6月以降」と書かれた時点の値 | 中（過小） |
| 基準日は正しく「2026年5月4日」と表示され、AI推定である旨も開示済み | （緩和要因） |

開示があるため「隠していた」わけではないが、**A の矛盾は開示では救えない**。

### 2-3. 設計上の構造的欠陥

1. **単一障害点が人間。** 週1回の手動更新に完全依存し、代替経路もアラートもない
2. **自動化が守りではなく攻撃側にいる。** auto_push.py は鮮度を判定せず Downloads を常に正とする。手動更新を破壊する方向に働いた
3. **鮮度の異常を検知する仕組みがない。** `updated` は表示されるだけで、古くなっても何も起きない
4. **更新頻度がデータの実在性と無関係。** 「週1回」は根拠なく決めた運用。裏づけとなる公開統計は月次しかない
5. **死にフィールドが判断を誤らせる。** `note` / `status` を書けば反映されると錯覚する構造

## 3. 再設計案（比較）

### 共通要件
- 算出根拠と計算式を公開できること
- ルートキー `A` / `B` / `C_US` / `C_GL` / `old` / `D`、キー名 `bpd` / `tankers_week` / `updated` は変更しない（§7 破壊条件）
- `normal_total_bpd` / `prev_bpd` / `label` / `color` は hormuz-data- が使うため削除しない

### 使える公開データ（実在を確認済み）

| ソース | 粒度 | 頻度・ラグ | 機械取得 |
|---|---|---|---|
| 財務省 貿易統計「品別国別表 輸入」（e-Stat） | 相手国別の原油輸入数量（kL） | 月次・翌月中旬に速報 | e-Stat API（appId登録要）／CSV |
| 資源エネルギー庁 石油統計速報 | 原油輸入量・中東依存度 | 月次 | Excel（自動化しにくい） |

**決定的な制約：公開統計は「相手国別」であって「ルート別」ではない。**

- `C_US` = 米国、`C_GL` = ブラジル＋ナイジェリア＋アンゴラ → **相手国から直接算出できる**
- `A`（フジャイラ経由）= UAE、`B`（東西PL）= サウジ → 相手国は取れるが、積出港・経路は統計に無い。
  ただし**ホルムズ封鎖下では「UAE産＝ADCOP／フジャイラ積出」「サウジ産＝紅海側／東西PL」と置ける**。
  これは明示すれば公開可能な仮定（封鎖が解除されたら成立しなくなる＝仮定の有効条件も併記する）
- `tankers_week` は統計から直接は出ない。`bpd → 隻/週` の換算式（VLCC積載量を定数化）で導出するか、廃止する

### 案の比較

#### 案1: 公開統計ベースの月次更新（自動）★推奨
- e-Stat API で貿易統計「品別国別表 輸入」から相手国別 原油輸入数量を取得
- kL/月 → 万BPD へ換算（`kL × 6.2898 bbl/kL ÷ 当月日数 ÷ 10,000`）
- 相手国 → ルートの対応表（`route_mapping`）を JSON に同梱して公開
- `tankers_week` は `bpd × 10,000 × 7 ÷ VLCC積載量(200万bbl)` で機械算出、定数も JSON に明記
- GitHub Actions で月次実行（`update_oil_flow.yml`）。既存の `update_eia.yml` と同じ構成が使える

| | |
|---|---|
| 長所 | 算出式を完全公開できる／再現可能／人手ゼロ／数値の裏に一次情報がある |
| 短所 | 統計ラグ1〜1.5か月（速報性を失う）／A・B は経路の仮定が必要／e-Stat appId の管理が要る |
| 適合 | 「算出根拠を公開できること」を唯一満たす案 |

#### 案2: 手動運用を継続し、算出手順書＋鮮度検知を足す
- 数値の作り方は変えず、`tools/oil-flow-procedure.md` に手順を明文化。JSON に `method` フィールドを追加
- `updated` から N 日超過で警告表示

| | |
|---|---|
| 長所 | 実装が軽い／速報性を維持できる |
| 短所 | **単一障害点が人間のまま**。一度途絶した運用を同じ設計で再開するだけ／「AI推定」の域を出ず、再現性が上がらない |
| 適合 | 単独では要件を満たさない |

#### 案3: 数値の掲載をやめ、定性表示に置き換える
- `bpd` / `tankers_week` の掲載を停止し、「稼働／限定／停止」の3段階のみ表示

| | |
|---|---|
| 長所 | 誤情報リスクが消える／運用コスト最小 |
| 短所 | サイトの情報価値が大きく落ちる／hormuz-data- 側のバー・合計・平常比%が全て機能しなくなる（§7 の破壊条件に抵触） |
| 適合 | 後退。最終手段 |

### 推奨: **案1 を本体に、案2 の「鮮度検知」を併用**

- 数値算出は案1（自動・公開可能）
- ただし A / B の経路仮定と、封鎖状況に依存する `old` / `D` の扱いは手動判断のまま残す（`manual_override` として分離し、どこが手動かを JSON 上で明示する）
- 鮮度検知は自動更新が壊れたときの保険として必ず入れる

### 自動／手動の切り分け

| 項目 | 区分 | 根拠 |
|---|---|---|
| `C_US` / `C_GL` の `bpd` | 自動 | 相手国別統計から直接 |
| `A` / `B` の `bpd` | 自動（仮定つき） | UAE／サウジの輸入量＋経路仮定 |
| `tankers_week` | 自動 | `bpd` からの換算式 |
| `old` / `D` の `bpd` | 手動 | 封鎖状況の判断。統計では分離不能。現状 0 固定 |
| `normal_total_bpd` | 半自動 | 封鎖前12か月平均から年1回算出 |
| `note` / `status` | — | 死にフィールド。削除するか、hormuz-data- 側で表示させるかを決める |

### 更新頻度の再検討

**週1回である必要はない。** 裏づけ統計が月次のため、週次更新しても新しい一次情報は無い。
→ **月次（貿易統計 速報公表後）を基本**とし、大きな事件（5/4 フジャイラ攻撃のような）が起きたときだけ手動で臨時更新する二層構成にする。

### 鮮度検知の実装案

- JSON に `updated_iso`（ISO8601）と `stale_after_days` を追加（既存 `updated` は表示用として残す＝破壊条件に触れない）
- hormuz-data- 側で経過日数を判定し、超過時は基準日を警告色＋「この値は N 日前のものです」と表示
- hormuz-map 側は §7 の決定により今回は無変更。将来 `#jf-basis-date` に同じ判定を足すかは別途
