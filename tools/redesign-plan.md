## 0. 大原則（順序を決めているルール）

1. **HTML構造の変更はドメイン移行の「前」、CSS見た目の変更は「後」**
   - 移行直後は検索評価の再計算が走る。同時にHTML構造を変えると順位変動の原因が切り分け不能になる
   - CSS（色・文字サイズ・カラム組）は検索評価に影響しないため移行後で安全
2. **`tools/migrate-domain.sh` はホスト名のリテラル置換のみ。ファイルパスを変えない限り改修と衝突しない**
   - CLAUDE.md「パス変更とホスト名置換を同一コミットに混ぜない」に従う
3. **フェーズをまたぐコミットを作らない。** 各フェーズは独立して revert できる状態を保つ

## 2. フェーズ0：CSS基盤整備（前提工事）— 完了（2026-09-04）

### 目的

`docs/index.html` は `:root` を1つも持たず、`font-size` が 447箇所（うちインライン `style` が 306箇所）に散在している。
この状態では「文字を少し大きく」という変更が447箇所の手作業になるため、先に一元化する。

### 実測された問題（2026-09-04）

- `:root` 定義が存在しない（`design-system.md` のトークンは未実装）
- `font-size` rem指定の分布: `0.75rem`×63 / `0.72rem`×62 / `0.78rem`×40 / `0.8rem`×29 / `0.85rem`×21
  - PC（16px基準）では 11〜12px 相当。可読下限 14px を大きく下回る
  - スマホは `@media (max-width:768px){html{font-size:18px}}` に救われているが、PC には救済がない
- `0.65〜0.78rem` の間に11段階が密集。設計ではなく偶然の集積
- px直指定が41箇所（6px〜26px）。rem基準の底上げが効かない
- メディアクエリのブレークポイントが 480 / 600 / 640 / 768 / 860px と5種混在（21箇所）

### 0a：トークン定義＋ブレークポイント統一（見た目不変）

- `:root` にタイポグラフィ・スペーシング・カラーのトークンを定義
- ブレークポイントを **768px / 1024px の2点**に統一（既存の 480/600/640/860 を吸収）
- **成功条件: 表示差分が出ないこと**

### 0b：既存値をトークンへ置換（段階統合）

- 密集した11段階を5段階へマッピング
- px直指定を rem/clamp へ（地図マーカー等、意図的な px は除外）
- 最小値を `0.875rem`（14px）に引き上げ、`0.7rem` 台を全廃

### 検証環境の制約（2026-09-04 に実際に誤判定した）

ローカル `file://` では**画像も iframe も読み込まれない**。
このため画像の代わりに `alt` テキストが展開され、実サイトには存在しない
はみ出しが観測される。実際に 375px で「横スクロール82px」と誤検出し、
不要な修正を加えかけた（実画像は 1672x941 で表示幅128px、はみ出しは発生しない）。

**レイアウトの最終確認は push 後の GitHub Pages で行うこと。**

### 禁止事項

- `@media (max-width:768px){html{font-size:18px}}` は削除・変更しない（CLAUDE.md 絶対ルール）
- コメントアウトタイトル `<!-- xxxx -->` を変更しない
- 原本を直接 `open(path,"w")` しない。一時ファイル＋`os.replace()`
- `sed -i` を CRLF ファイルに使わない

## 3. フェーズ1：コンテンツ整理（A案・3層ピラミッド型）

### 現状の重複

同一情報が最大4箇所に出ている:
`30秒サマリー` / `情勢カード×3` / `全ルート現況サマリー`（長大な1段落）/ `速報インシデント` / `最新ニュース`

### A案の構造

情報を「深さ」で階層化し、重複を「要約→詳細」の正当な関係に変える。

```
第1層 いま何が起きているか  ← 30秒サマリー＋情勢カード（統合）
第2層 どう影響するか        ← 地図・ルート表・シナリオ・市場
第3層 なぜそうなのか        ← コラム・全文・アーカイブ・出典
```

統合対象:
- 情勢カード → 30秒カラムへ吸収
- 「全ルート現況サマリー」の長文 → ルート表の各行へ分解

### 1a / 1b の分割（移行スケジュールの都合）

| | 内容 | 時期 | リスク |
|---|---|---|---|
| **1a** | セクション名の `h2`/`h3` タグ化のみ | ドメイン移行**前** | 低（見た目ほぼ不変） |
| **1b** | セクション統合・再配置（A案本体） | ドメイン移行**後** | 中 |

1a を移行前に行う理由: 現状の見出しタグは `h1`×1・`h2`×3 のみで、
セクション名はすべて `div`/`span`。この状態で移行すると誤った構造のまま評価が引き継がれる。
タグ差し替えだけで SEO 効果の大半を確保でき、リスクが低い。

（コンテナ `max-width:1400px` の1カラムで全角90字近くになっている）。

## 7. oil-flow.json スキーマ契約（依頼6を進める前に必読）

2026-09-04 に両リポジトリを実測して確認した依存関係。
`data/oil-flow.json` には**消費者が2つ**あり、使うフィールドが異なる。
片方だけを見て再構築すると、もう片方が静かに壊れる。

### 消費者1: `hormuz-data-`（ダッシュボード本体）

`hormuz-data-/index.html` の `initJapanFlow()`。**ほぼ全フィールドを使用**する。

| フィールド | 用途 |
|---|---|
| `normal_total_bpd` | 平常比パーセントの分母（未指定時は 236 にフォールバック） |
| `updated` | `#jf-updated` に表示 |
| `routes.*.bpd` | 合計値・バー幅・表示値 |
| `routes.*.prev_bpd` | 前週差分（▲▼）の算出 |
| `routes.*.tankers_week` | `🚢×N` 表示 |
| `routes.*.label` | ルート名表示 |
| `routes.*.color` | バーとラベルの配色 |
| ルート順 | `ORDER = ['old','A','B','C_US','C_GL','D']` を**コード側に直書き**している |

### 消費者2: `hormuz-map`（このサイト）

`docs/index.html` の `loadRouteTableFlow()`。**3種類しか使わない**。

| フィールド | 注入先 |
|---|---|
| `updated` | `#jf-basis-date`（ルートテーブルの「基準日」表示） |
| `routes.{A,B,C_US,C_GL}.bpd` | `#jf-{key}-bpd` |
| `routes.{A,B,C_US,C_GL}.tankers_week` | `#jf-{key}-tanker` |

`normal_total_bpd` / `prev_bpd` / `label` / `color` / `status` / `note` は**未使用**（実測: 参照0箇所）。

### 変更時の破壊条件

- **キー名 `bpd` / `tankers_week` / `updated` の改称** → 両方が壊れる
- **ルートキー `A` / `B` / `C_US` / `C_GL` の改称・削除** → hormuz-map のルートテーブルが `—` 表示になる
- **`old` / `D` の改称・削除** → hormuz-data- のみ影響（下記のとおり hormuz-map は静的）
- **`normal_total_bpd` / `prev_bpd` / `label` / `color` の削除** → hormuz-data- のみ壊れる
- ルートを**追加**する場合、hormuz-data- は `ORDER` 配列に、hormuz-map は `MAP` オブジェクトに
  それぞれ手で追記しないと表示されない（どちらもキーをコードに直書きしている）

### 既知の不整合（依頼6で解消すべき点）

1. **`updated` が「2026年5月4日 JST」のまま**（2026-09-04 時点で約4か月前）。
   この値は hormuz-map のルートテーブル基準日として**そのまま公開表示されている**。
2. **`old` と `D` は hormuz-map 側では JSON を見ていない。**
   該当セルは HTML に「停止中 / — 隻/週」と直書きされた静的値
   （`<td id="jf-td-old">` / `<td id="jf-td-D">` に注入用 id が無い）。
   JSON で `old`/`D` の `bpd` を変えても hormuz-map には反映されない。
   反映させたい場合は `docs/index.html` 側に `id="jf-old-bpd"` 等を追加し、
   `loadRouteTableFlow()` の `MAP` にキーを足す必要がある。
3. `tankers_week` は「週あたり寄港タンカー隻数推定」だが、算出根拠が
   `_comment` の一文しかなく、サイト側にも「算出方法の詳細は現在整理中です」と表示されている。

### 変更後の検証手順（必須）

`oil-flow.json` を編集するのは `hormuz-data-` 側だが、**影響は `hormuz-map` にも出る**。
気づかないまま公開される経路があるため、必ず両方を確認する。

**前提: `file://` や LiveServer では確認できない。** iframe と fetch が動かないため、
必ず GitHub Pages に push してから確認すること。

1. `hormuz-data-` を push し、Pages の反映を待つ（1〜2分）
2. https://yattanda.github.io/hormuz-map/ を**強制リロード**（Ctrl+F5）で開く
3. ブラウザのコンソールで以下を実行する

```javascript
// ルートテーブルへの注入結果を一覧する
(() => {
  const r = ['A','B','C_US','C_GL'].map(k => ({
    route: k,
    bpd: document.getElementById('jf-'+k+'-bpd')?.textContent,
    tanker: document.getElementById('jf-'+k+'-tanker')?.textContent
  }));
  console.table(r);
  console.log('基準日:', document.getElementById('jf-basis-date')?.textContent);
})();
```

**判定基準**

| 症状 | 意味 |
|---|---|
| `bpd` が `—` のまま | そのルートキーが JSON 側に無い（改称・削除された） |
| `tanker` が `— 隻/週` のまま | `tankers_week` が 0 か欠落 |
| 基準日が `—` | `updated` が欠落 |
| 基準日が古い日付 | `updated` の更新漏れ（値を変えたら `updated` も必ず更新する） |
| コンソールに `oil-flow fetch error` | JSON が壊れている / URL が変わった |

4. `hormuz-data-` 側のダッシュボードでも「日本向け調達フロー」の
   合計値・平常比%・各ルートのバーと ▲▼ が正しいことを確認する
   （`normal_total_bpd` と `prev_bpd` はこちらでしか使われていないため、
   hormuz-map 側の確認だけでは検出できない）

### 依頼6を始める前に決めておくこと

`old` と `D` を hormuz-map のルートテーブルにも反映させるかどうかで、
作業範囲が変わる。

| 方針 | 作業 |
|---|---|
| 反映させない（現状維持） | `hormuz-data-` 側のみ。hormuz-map は無変更 |
| 反映させる | `docs/index.html` に `id="jf-old-bpd"` 等を追加し、`loadRouteTableFlow()` の `MAP` にキーを追記する。**hormuz-map 側の変更が必要**になるため、フェーズ1a/1b と作業が競合しないよう順序を決めること |

**決定（2026-09-04）: 「反映させない（現状維持）」を採用。**

- 依頼6は `hormuz-data-` 側のみで完結させる。`docs/index.html` は変更しない
- 理由: 封鎖が継続している間は「停止中 / — 隻/週」の静的表示が実質正しく、
  急ぐ必要がない。またドメイン移行前に `docs/index.html` を触る回数を
  減らしたいため（変更が増えるほど移行時の切り分けが難しくなる）
- 封鎖が解除され `old` / `D` に実数が入る段階になったら、改めて着手する

**問題点**

- 同じ階層の見出しが `0.75 / 0.92 / 1.0 / 1.2rem` の4サイズ（最大1.6倍差）
- 見出しが存在しないセクションが4つ
- 既存の見出しタグ5個の出現順が `h1 → h3 → h4 → h2 → h3` で階層が破綻
- セマンティック要素は `nav`×1・`section`×1 のみ。`main` / `article` / `aside` はゼロ

### 目標とする階層

1a では**セクションの並び順は変更しない**（並べ替えはフェーズ1b で行う）。
各主要セクションを `h2` に統一し、その内部の小見出しを `h3` にする。

```
h1  ホルムズ海峡危機マップ                    ← 既存・変更しない
├ h2  30秒で全体像を把握
├ h2  いま起きていること（情勢カード）
├ h2  ホルムズ データ監視ダッシュボード        ← 新設
├ h2  リアルタイム市場（原油・為替・貴金属）    ← 新設
├ h2  海峡周辺マップ                          ← 新設
│  └ h4 凡例                                 ← 既存 h4。h3 へ繰り上げ
├ h2  主要指標                                ← 新設
├ h2  速報インシデント                        ← ボタン内 span から構造分離
├ h2  ルート別現況                            ← 本文600字を分離
├ h2  4つのシナリオ
│  └ h3 次の焦点 5つ                         ← 既存 h3。階層が合う
├ h2  特別解説コラム
│  └ h3 各コラムのタイトル
├ h2  トランプ大統領 2つの声明 全文日本語訳    ← 既存 h2.bw-title。そのまま
├ h2  関連最新ニュース
├ h2  現地メディア視点
└ h2  出典・更新ログ
```

**フェーズ1b（A案の3層ピラミッド）との関係**

1b で「第1層／第2層／第3層」の層見出しを導入する場合、
層を `h2`・各セクションを `h3` に一段下げる選択肢と、
層は視覚的なグルーピングに留めてセクションを `h2` のまま維持する選択肢がある。
**1b でセクションの並べ替えを行うときに合わせて決める**（1a では判断しない）。
